# Failure Test Scenarios

Run these the same way Assignment 2's AZ-outage test was run: in the **Cloud Architecture Lab** simulator (`https://main.d35uam9e2t7o65.amplifyapp.com/#lab`), using an import built from this assignment's architecture (`Export → Upload JSON` → `evidence/lab-import.json`, generated by `architecture/generate_lab_import.py`). This import is already confirmed working — `evidence/s1.png` shows it loaded and rendering correctly, all 42 nodes including the new DynamoDB table and the 4 new VPC interface endpoints. Each scenario below is measured against the brief's RPO (≤5 min) and RTO (≤1 hour) targets, states expected impact *before* running it, and names the fix if impact exceeds target.

For each scenario, capture in `evidence/`: the Failure Lab "Impact" badge, the Event Timeline for a request re-run during the injected failure, and the HTTP status / latency of that re-run.

## Scenario 1 — Availability Zone A outage, exam month (dual-NAT state)

**Setup:** inject the Failure Lab's AZ outage on `AZ-A`, with `single_nat_gateway=false` (exam-month state — both NAT Gateways present, matching the A2 test this extends).

**Expected impact:**
- Aurora writer (AZ-A) fails; automatic Multi-AZ promotion of the AZ-B reader to writer.
- Lambda ENIs in AZ-A's private subnet become unreachable; API Gateway routes new invocations to AZ-B's Lambda ENIs (API Gateway/Lambda have no AZ affinity — this is automatic, not a failover *action*).
- NAT-A and RDS Proxy's AZ-A target become unreachable; NAT-B and RDS Proxy's AZ-B target absorb all traffic — no impact, since NAT is still dual.
- A request re-run mid-outage should still return HTTP 200, same as the Assignment 2 test.

**Measured against targets:**
- **RPO:** 0 — no in-flight write is lost; the last acknowledged autosave (DynamoDB, multi-AZ on write) and Aurora write (acknowledged only after durable Multi-AZ storage) both survive.
- **RTO:** Aurora failover typically completes in 30–120 seconds, well inside the 1-hour target.

**If impact exceeds target:** none expected; this scenario should pass cleanly, as it did in Assignment 2. If the re-run returns a 5xx instead of 200, the likely cause is a stale RDS Proxy connection pool not yet re-targeted to the new writer — the fix is RDS Proxy's own automatic target re-resolution (no customer action), or, if that's slow in the simulator, reducing `max_idle_connections_percent` so the pool cycles connections faster.

## Scenario 2 — Availability Zone B outage, normal month (single-NAT state)

**Setup:** inject the Failure Lab's AZ outage on `AZ-B`, with `single_nat_gateway=true` (normal-month state — only NAT-A, in AZ-A, exists).

**Expected impact:**
- Aurora reader (AZ-B) becomes unreachable; writer (AZ-A) is unaffected since the fault is on the opposite AZ from NAT.
- Lambda ENIs in AZ-B's private subnet become unreachable; API Gateway routes to AZ-A's Lambda ENIs.
- NAT-A (AZ-A) is untouched by a B-side fault, so NAT-dependent egress is unaffected — this is the "good half" of the single-NAT trade-off: an AZ-B outage, specifically, costs nothing extra beyond the standard AZ-loss tolerance already covered by scenario 1's logic in reverse.
- A request re-run mid-outage should return HTTP 200.

**Measured against targets:**
- **RPO:** 0, same reasoning as scenario 1.
- **RTO:** well inside 1 hour — this scenario has no NAT-related recovery step at all, since the surviving NAT (AZ-A) was never dependent on AZ-B.

**If impact exceeds target:** none expected. This scenario exists specifically to demonstrate that the single-NAT optimization (§ CHANGE_LOG #4) is *asymmetric* — it only bites on an AZ-A fault (scenario 4), not an AZ-B fault — which is a finding worth having evidence for, not just asserting.

## Scenario 3 — Exam-week capacity burst: Aurora ACU ceiling under combined peak load

**Setup:** simulate (or, if the simulator doesn't model ACU scaling directly, reason through using the load test in `infra/load-test.md`) two large exams peaking within the same 5-minute window — effectively doubling the single-exam 3,000-student peak this architecture is sized for, to find where the margin actually runs out.

**Expected impact:**
- API Gateway/Lambda: no ceiling, scale to the burst (Lambda's regional concurrency limit is in the tens of thousands; reserved concurrency per function is the real cap and is a Terraform-configurable value, not a hard architecture limit).
- DynamoDB (autosave answers, On-Demand): absorbs the write burst with no provisioned-capacity ceiling to hit — this is precisely why autosave was moved here (CHANGE_LOG #6).
- Aurora Serverless v2: **does** have a hard ceiling — `aurora_max_capacity = 4` ACU (`infra/variables.tf` in Assignment 2, carried forward unchanged). Under a genuinely combined worst case (two 1,500+-student exams opening simultaneously, each needing `open-exam` + `submit-exam` writes against Aurora), connection/ACU pressure from exam-open and exam-submit bursts (not autosave, which is now on DynamoDB) could approach or hit the 4-ACU ceiling, causing RDS Proxy to queue connections and increasing p99 latency on `open-exam`/`submit-exam` — a slowdown, not a 5xx, as long as RDS Proxy's connection queue doesn't itself time out client requests.

**Measured against targets:**
- **RPO:** unaffected — DynamoDB autosave is the RPO-critical path and has no ceiling.
- **RTO:** not a failure in the outage sense (nothing is down), but a **sustained latency spike** during the worst 5–10 minutes of a combined-exam peak is a real degraded-service risk the brief's RTO/RPO framing doesn't directly capture.

**Fix:** raise `aurora_max_capacity` (e.g. to 8 ACU) ahead of any exam week where two large cohorts are scheduled to open within the same window — a one-line `terraform apply`, no architecture change. Longer-term, if this becomes routine, move `open-exam`/`submit-exam` reads to the Aurora reader via RDS Proxy's read/write splitting to spread the connection load. This is flagged as a capacity risk to load-test (see `infra/load-test.md`), not assumed away.

## Scenario 4 — Availability Zone A outage, normal month (single-NAT state) — the accepted trade-off, tested

**Setup:** inject the Failure Lab's AZ outage on `AZ-A`, with `single_nat_gateway=true` (normal-month state — the sole NAT Gateway, NAT-A, lives in AZ-A).

**Expected impact:**
- Same Aurora/Lambda/API Gateway failover behaviour as scenario 1 (writer promotion, Lambda routed to AZ-B) — the **student-facing exam path is unaffected**, because `open-exam`, `autosave` (now DynamoDB), `submit-exam`, `presign-upload` and `release-results` all reach their dependencies (Aurora via RDS Proxy, DynamoDB, S3, SQS, Secrets Manager, Cognito, KMS) through AZ-redundant paths or VPC endpoints that don't route through NAT at all (CHANGE_LOG #5).
- **NAT-A is lost along with the rest of AZ-A**, and because it was the *only* NAT Gateway, NAT-dependent egress breaks region-wide (not just for AZ-B) until it's recreated.
- The only traffic that actually needs NAT in this architecture is whatever has no VPC endpoint equivalent — in the current service list that's effectively nothing in the student-facing request path (SES now has an interface endpoint too), so this failure is expected to be **invisible to students and tutors** during the outage.

**Measured against targets:**
- **RPO:** 0 — unaffected, same as scenario 1.
- **RTO:** the exam-facing service itself recovers inside the same ~30–120s as scenario 1. The NAT Gateway specifically takes longer to recreate (a few minutes via `terraform apply -var single_nat_gateway=false`, or AWS's own AZ recovery), but since nothing on the critical path depends on it, this doesn't extend the *effective* RTO for the service the RPO/RTO targets are actually protecting.

**If impact exceeds target:** if testing surfaces a dependency on NAT that wasn't expected (e.g. a Lambda cold-start needing an external npm registry call, or a future third-party integration with no VPC endpoint), the fix is immediate: flip `single_nat_gateway` back to `false` — a single tfvar and `terraform apply`, reverting to Assignment 2's always-dual-NAT posture at the cost of the ~US$44/month (Singapore) this optimization was saving in that month. This is exactly why the toggle, not a permanent architectural removal of the second NAT Gateway, was chosen.
