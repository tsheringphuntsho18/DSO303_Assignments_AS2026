# Service Documentation — EduExam Platform

System name used throughout this repo: **EduExam** (`eduexam` resource prefix). Serverless architecture: Amazon API Gateway + AWS Lambda for compute, Aurora PostgreSQL Serverless v2 (Multi-AZ) for the database, S3 for files, SQS/EventBridge for async marking and notifications.

| Service | Role | Configuration | Why over an alternative | Connects to |
|---|---|---|---|---|
| **Amazon Route 53** | DNS for `eduexam.example.com`; health-checked failover | Public hosted zone; A/AAAA alias records to CloudFront; health check on `/healthz` | Native AWS health-check failover and alias records (no extra charge, no CNAME flattening issues) beat an external DNS provider for AWS-native failover and IAM-controlled change control | CloudFront |
| **AWS WAF** | Blocks SQLi/XSS/bot traffic and rate-limits login and autosave endpoints before they reach the app | Web ACL with `AWSManagedRulesCommonRuleSet`, `AWSManagedRulesKnownBadInputsRuleSet`, and a rate-based rule (2,000 req/5 min per IP) on `/api/*`; attached to the CloudFront distribution | Attaching WAF at the CloudFront edge filters malicious traffic once for both static and API paths, which is cheaper and lower-latency than running a WAF per-region or relying on application-level filtering in Lambda | CloudFront |
| **Amazon CloudFront** | Edge CDN for the SPA frontend and single entry point that fans out `/api/*` to API Gateway | 2 origins (S3 OAC for `/*`, API Gateway for `/api/*`); HTTPS only (ACM cert); cache disabled on `/api/*`, cached+compressed for static assets | A CDN absorbs the exam-week static-asset load (JS/CSS/exam instructions) at the edge instead of the origin, and terminating TLS at ~400+ edge locations cuts latency for students versus serving directly from one region | Route 53, S3 (frontend), API Gateway, WAF, ACM |
| **AWS Certificate Manager (ACM)** | TLS certificates for CloudFront and the API custom domain | DNS-validated public certs in `us-east-1` (required for CloudFront) | Free, auto-renewing, IAM-integrated — no manual renewal process to miss before an exam window | CloudFront, API Gateway |
| **Amazon Cognito** | Role-based sign-in for students, tutors and administrators; issues JWTs | User Pool with 3 groups (`student`, `tutor`, `admin`), MFA optional for staff groups, password policy enforced; App Client (no client secret, SPA flow); used as a native API Gateway JWT authorizer | A managed identity provider removes the need to build/secure password storage, MFA and token issuance ourselves, and its group claims map directly to API Gateway/Lambda authorization without a custom auth service | API Gateway, Lambda (claims in event context) |
| **Amazon API Gateway (HTTP API)** | Single API entry point: start exam, autosave answers, request upload URL, release results | Routes per Lambda function; Cognito JWT authorizer on all routes except health check; throttling 1,000 req/s burst 2,000 (covers the 3,000-students-in-5-min peak spread across routes) | An HTTP API scales automatically to the exam-week spike with no capacity planning, unlike an ALB+EC2 fleet which needs pre-warming or scheduled scaling ahead of a known 5-minute burst | Lambda, Cognito |
| **AWS Lambda** | Stateless compute for all API routes (`open-exam`, `autosave`, `presign-upload`, `release-results`) and async workers (`automark`, `notify-tutor`, `send-email`) | Node.js 20.x, 256–512 MB, attached to both private subnets (2 AZs) via an ENI, reserved concurrency set per function to protect the database | Pay-per-invocation compute scales from near-zero at 03:00 to 3,000 concurrent exam starts without any pre-provisioned fleet, which is both cheaper and faster to scale than ECS/EC2 for this bursty, request-driven load | API Gateway, Aurora (via RDS Proxy), S3, SQS, Secrets Manager, EventBridge, IAM |
| **Amazon VPC** | Network isolation for the database and Lambda-to-database traffic | `10.0.0.0/16`, 2 AZs, 2 public + 2 private subnets, no resources directly internet-routable except NAT | Keeps the database and Lambda-RDS Proxy traffic off the public internet, which is required to meet the "encryption in transit, private data path" target | All compute/data resources |
| **Internet Gateway** | Internet egress/ingress for the public subnets | One per VPC | Standard AWS-managed edge device; no self-hosted alternative makes sense | Public subnets, NAT Gateways |
| **NAT Gateway** | Outbound-only internet access for Lambda-in-VPC (e.g. calling SES, Cognito) | One NAT Gateway per AZ (2 total), each in its own public subnet, each private subnet routes to the NAT in its own AZ | A NAT Gateway per AZ avoids a cross-AZ single point of failure — one NAT instance (EC2-based) would fail with its AZ and is also an unmanaged, patch-it-yourself alternative | Public subnets, private-subnet route tables |
| **Amazon Aurora PostgreSQL Serverless v2** | System of record: users, exams, questions, answers, submissions metadata, results | Multi-AZ cluster (1 writer + 1 reader, different AZs), 0.5–4 ACU auto-scaling, storage encrypted with KMS, automated backups (35-day retention) + continuous backtrack | Aurora's storage layer replicates across 3 AZs automatically and fails over in under 30 seconds, and Serverless v2 scales capacity to the exam-week spike without resizing an instance by hand the way standard RDS would require | RDS Proxy, Secrets Manager, KMS |
| **Amazon RDS Proxy** | Connection pooling between bursty Lambda invocations and Aurora | Attached to the Aurora cluster, IAM authentication enabled | Each exam-start can spawn hundreds of concurrent Lambda executions; without pooling they would exhaust Aurora's max_connections in seconds, which a direct Lambda→Aurora connection (the alternative) cannot survive at this concurrency | Aurora, Lambda, Secrets Manager |
| **Amazon S3 — `eduexam-submissions`** | Stores assignment uploads (PDF/ZIP, up to 50 MB) | Versioning on, SSE-KMS, lifecycle: Standard → Standard-IA at 90 days → Glacier Deep Archive at 365 days → expire at 1,825 days (5 years); EventBridge notifications enabled | Cheaper and more durable (11 nines) than EBS/EFS for write-once files, and presigned PUT URLs let the browser upload the 40–50 MB file directly to S3, keeping large payloads off API Gateway's 10 MB request limit and off the Lambda execution path entirely | CloudFront (not exposed directly), Lambda (presign + read), EventBridge, KMS |
| **Amazon S3 — `eduexam-frontend`** | Hosts the built SPA (HTML/JS/CSS) | Private bucket, read only via CloudFront Origin Access Control (OAC) | Static hosting from S3+CloudFront is far cheaper and simpler to scale than running a web server fleet for assets that never change per-request | CloudFront |
| **S3 Gateway Endpoint** | Private route from the VPC to S3 for Lambda | Attached to both private-subnet route tables | Lets Lambda read/write S3 (e.g. fetching a submission for marking) without routing through the NAT Gateway, which is both cheaper (no NAT data-processing charge) and keeps traffic off the public internet path | Private subnets, S3 |
| **Amazon SQS — `marking-queue` / `email-queue`** | Decouples MCQ auto-marking and result-release emails from the request path | Standard queues, visibility timeout 60s, redrive policy to a DLQ after 5 failed attempts | Queuing marking/email work means a burst of exam submissions or a slow SES call never blocks the student-facing API, and a failed job retries instead of silently dropping a mark or email | Lambda (producer + consumer), DLQ |
| **SQS Dead-Letter Queues** | Captures marking/email jobs that fail repeatedly, for investigation | 1 DLQ per queue, CloudWatch alarm on `ApproximateNumberOfMessagesVisible` > 0 | Without a DLQ a poison-pill message (e.g. a corrupt submission) would retry forever or vanish; this gives an auditable trail, which matters for a 5-year academic record requirement | CloudWatch, SQS |
| **Amazon EventBridge** | Routes S3 "new submission" events to the tutor-notification Lambda; schedules housekeeping | Rule on `eduexam-submissions` `Object Created` events → `notify-tutor` Lambda target | A native S3→EventBridge→Lambda event path needs no polling and no extra message broker, unlike having Lambda poll S3 or a cron job scan for new keys | S3, Lambda |
| **Amazon SES** | Sends "results released" and "assignment received" emails | Verified domain identity, configuration set with CloudWatch delivery metrics | Purpose-built, high-deliverability email service at a fraction of the cost/operational effort of self-hosting SMTP, with built-in bounce/complaint handling needed to protect the sending domain | Lambda (`send-email` worker), CloudWatch |
| **AWS Secrets Manager** | Stores the Aurora master credentials and SES/API secrets | Automatic rotation every 30 days for the DB secret, resolved at runtime by RDS Proxy/Lambda | Rotates credentials without a redeploy and without the secret ever appearing in code, env files or Terraform state in plaintext, unlike Parameter Store's manual-rotation model | Lambda, RDS Proxy, Aurora, KMS |
| **AWS KMS** | Encryption key management for S3, Aurora, Secrets Manager and CloudWatch Logs | One customer-managed key (`eduexam-key`), automatic yearly rotation | A customer-managed key gives auditable, revocable control over who can decrypt 5-year academic records, which the AWS-managed default key does not expose in CloudTrail to the same granularity | S3, Aurora, Secrets Manager, CloudWatch Logs |
| **Amazon CloudWatch** | Metrics, logs, alarms and the operations dashboard | Log groups per Lambda (14-day retention) and API Gateway access logs; alarms on API 5xx rate, Lambda errors/throttles, Aurora CPU/connections, SQS DLQ depth; one dashboard (`eduexam-ops`) | Native, zero-agent metrics/logs for every service in this design versus standing up and licensing a third-party observability stack for a platform this size | All services (via EMF/agent-less integration) |
| **AWS CloudTrail** | Audit log of every API call against the AWS account (who changed what, when) | Multi-region trail, logs to a dedicated, versioned, access-logged S3 bucket | Required for the 5-year compliance/audit trail on an exam platform; without it, an access dispute (e.g. "was a result edited after release?") has no evidence | S3 (trail bucket), CloudWatch Logs |
| **AWS IAM** | Least-privilege roles for every Lambda, CI/CD pipeline and human user | One execution role per Lambda function (scoped to only the tables/buckets/queues it touches); a dedicated GitHub Actions OIDC role for deploys (no long-lived access keys) | Per-function roles contain the blast radius of a compromised function to exactly what it needs, versus one shared execution role that would let any function touch any resource | Every AWS service |
| **GitHub Actions + Terraform** | CI/CD: `terraform plan`/`apply` on push to `main`, builds and deploys Lambda packages, syncs the frontend to S3, invalidates CloudFront | OIDC federation (no static AWS keys stored in GitHub); `infra/` is the single source of truth for all resources above | A code-defined pipeline with OIDC is reproducible from a clean AWS account and leaves no long-lived credentials in CI, unlike a console-built pipeline or a CI user with static access keys | All AWS services (via Terraform provider) |
